# 코드 리뷰 및 배포 규정

## Git 브랜치 전략 및 PR 규칙
넥사테크 개발본부는 민첩한 배포와 높은 코드 품질을 위해 Trunk-Based Development 방식을 표준으로 채택합니다.
- **기본 브랜치**: `main` (항상 배포 가능한 안정 상태 유지).
- **작업 브랜치 명명 규칙**:
  - 신규 기능: `feat/ENG-{이슈번호}-{기능명}` (예: `feat/ENG-104-bm25-indexer`)
  - 버그 수정: `fix/ENG-{이슈번호}-{수정내용}` (예: `fix/ENG-209-rejection-threshold`)
  - 문서/인프라: `docs/...`, `chore/...`, `refactor/...`
- **풀 리퀘스트(PR) 필수 규칙**:
  - 모든 PR은 명확한 작업 목적, 테스트 방법, 스크린샷(UI 변경 시)을 포함해야 합니다.
  - 최소 1인 이상의 동료 엔지니어(Peer Reviewer)로부터 `Approve`를 득해야 머지 가능합니다.
  - CI 파이프라인(린트, 타입 체크, 단위 테스트, 보안 취약점 스캔)이 100% 통과되어야 합니다.

## 코드 리뷰 가이드라인
코드 리뷰는 상호 배움과 품질 유지를 위한 협업 프로세스입니다.
- **리뷰 회신 시간**: PR 요청 수신 후 24시간 이내(영업일 기준)에 1차 피드백 또는 승인을 완료해야 합니다.
- **중점 검토 항목**:
  1. **정확성 및 비즈니스 로직**: 요구사항 충족 및 엣지 케이스 처리 여부.
  2. **보안 취약점**: 하드코딩된 API Key/비밀번호, SQL Injection, RBAC 접근 제어 누락 여부 검증.
  3. **성능 및 확장성**: 비효율적인 DB 쿼리(N+1 문제), 불필요한 리렌더링, 메모리 누수 방지.
  4. **가독성 및 테스트 코드**: 클린 코드 원칙 준수 및 의미 있는 테스트 커버리지 확보.

## CI/CD 파이프라인 및 스테이징 배포
- **GitHub Actions 기반 자동화**: `main` 브랜치로 머지 시 자동으로 도커 이미지 빌드 및 취약점 검사가 실행됩니다.
- **스테이징 환경 자동 배포**: 머지 즉시 사내 스테이징 환경(`https://staging-rag.nexatech.internal`)에 카나리 배포되며, E2E 통합 테스트가 트리거됩니다.
- **품질 게이트 (SonarQube & Snyk)**: 코드 스멜 0건, 보안 취약점 Critical/High 0건을 통과해야 배포가 승인됩니다.

## 프로덕션 배포 및 배포 동결 시간(Deployment Freeze)
- **정기 배포 시간**: 안정적인 장애 대응을 위해 매주 **화요일 ~ 목요일 10:00 ~ 16:00** 사이에만 프로덕션을 배포합니다.
- **배포 동결(Deployment Freeze) 정책**:
  - **금요일 14:00 이후 및 공휴일 전날**: 프로덕션 신규 배포를 전면 금지합니다.
  - **예외 처리**: 서비스 다운, 심각한 보안 결함 등 크리티컬 핫픽스(Hotfix)에 한하여 CTO 사전 승인 후 예외 배포 가능합니다.
- **무중단 롤링 배포**: 쿠버네티스(k8s) 롤링 업데이트 및 헬스체크 프로브를 통해 트래픽 중단 없는 무중단 배포를 보장합니다.
